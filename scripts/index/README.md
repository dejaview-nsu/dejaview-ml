# Индексация фильма

Скрипт `scripts/index/` проводит один фильм по потоку индексации из #17393 п. 4: видеофайл на диске
превращается в эмбеддинги в четырёх коллекциях Qdrant, метаданные TMDB - в строку таблицы `movies`.
После успешного запуска фильм находится поиском.

Это офлайн-инструмент оператора, в production он не входит. Запускается на машине оператора,
к PostgreSQL и Qdrant подключается через SSH-туннель.

## Установка

Из корня репозитория, Python 3.11+. Нужен ffmpeg с ffprobe в `PATH` (`apt install ffmpeg`,
`brew install ffmpeg`, под Windows - сборка с https://ffmpeg.org/download.html).

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
# torch ставится до остальных зависимостей, иначе pip скачает сборку с CUDA на несколько гигабайт.
# Версия - как в CI и Dockerfile ML-сервиса.
pip install "torch==2.13.0" --index-url https://download.pytorch.org/whl/cpu      # без видеокарты
# pip install "torch==2.13.0" --index-url https://download.pytorch.org/whl/cu126  # с видеокартой NVIDIA
pip install -r scripts/index/requirements.txt
cp scripts/index/.env.example scripts/index/.env   # и заполнить
```

`requirements.txt` ставит пакет ML-сервиса `dejaview_ml` из корня репозитория (`-e .`): эмбеддинги
строятся его кодом. Поэтому команду нужно запускать из корня.

При первом запуске скачиваются веса четырёх моделей, около 3 ГБ, в `ML_CACHE_DIR`
(по умолчанию `.cache/huggingface` в текущей папке). Дальше они берутся из кэша.

## Запуск

```bash
python -m scripts.index path/to/movie.mp4 --movie-id 603
```

`--movie-id` - id фильма в TMDB: число из адреса страницы, `https://www.themoviedb.org/movie/603-the-matrix` → `603`.
Один фильм за запуск.

| Команда | Что делает |
|---|---|
| `python -m scripts.index movie.mp4 --movie-id 603` | индексирует фильм |
| `python -m scripts.index movie.mp4 --movie-id 603 -v` | то же с подробным логом и трассировкой ошибок |
| `python -m scripts.index movie.mp4 --movie-id 603 --env-file path/.env` | другой файл окружения |

Повторный запуск по тому же фильму безопасен: дубликаты не появляются. ID точки в Qdrant
вычисляется из фильма и смещения фрагмента, а перед записью скрипт удаляет все старые точки фильма.
Если исходник заменили и нарезка изменилась, точки от старой нарезки в поиске не останутся.

### Требования к файлу

#17395 п. 2.3: контейнер MP4, видео H.264, звук AAC, качество 480p (кадр не больше 854×480,
широкоэкранный фильм 854×358 подходит). Неподходящий файл отклоняется со списком причин, например:

```
Файл movie.mkv не подходит для индексации (#17395 п. 2.3: MP4, H.264, AAC, не больше 854×480):
  - контейнер matroska,webm, нужен MP4
  - кадр 1920×800, нужен 480p: не больше 854×480
Пережмите его, например:
  ffmpeg -i in.mkv -map 0:v:0 -map 0:a:0 -c:v libx264 -c:a aac -vf "scale=854:480:force_original_aspect_ratio=decrease:force_divisible_by=2,setsar=1" out.mp4
```

## Что происходит при запуске

В логе каждый этап начинается строкой `Этап N/6`, долгие этапы показывают прогресс `N из ~M`.

1. **Проверка файла** через ffprobe: контейнер, кодеки, размер кадра, длительность.
2. **Проверка Qdrant и PostgreSQL**: четыре коллекции на месте, размерность и метрика совпадают с моделями;
   БД отвечает, таблица `movies` есть. Коллекции и таблицу скрипт не создаёт: коллекции создаёт ML-сервис
   при старте, таблицу - миграции `dejaview-backend`.
3. **Метаданные из TMDB** записываются в `movies` (`INSERT ... ON CONFLICT DO UPDATE`). Новый фильм получает
   `indexed_at = NULL`. У уже проиндексированного `indexed_at` не меняется: при повторной индексации он остаётся
   в поиске со старыми векторами, пока считаются эмбеддинги, и при сбое на этапе 4 там и остаётся.
   Здесь же отклоняется фильм, которого нет в TMDB или у которого нет русского названия, описания или постера.
4. **Нарезка и эмбеддинги**, по модальностям. ffmpeg отдаёт кадры и звук потоком, на диск нарезки не пишутся.

   | Коллекция | Фрагмент | `offset_sec` |
   |---|---|---|
   | `text` | русское описание из TMDB, как `passage: <текст>` | нет |
   | `image` | кадр каждые 5 с | 0, 5, 10, ... |
   | `video` | сегмент 10 с без перекрытия, 1 кадр в секунду; хвост короче 10 с тоже сегмент | 0, 10, 20, ... |
   | `audio` | окно 10 с с шагом 5 с; окно у конца фильма короче, короче 1 с отбрасывается | 0, 5, 10, ... |

   Модели, ревизии весов и предобработка - те же, что в ML-сервисе (`dejaview_ml`): иначе векторы фрагментов
   и запросов несравнимы.
5. **Запись в Qdrant**: `indexed_at = NULL`, удаление старых точек фильма во всех четырёх коллекциях, запись новых
   пачками, затем `indexed_at = now()`. С этого момента фильм находится поиском.
6. **Очистка**. Временная папка в рабочем каталоге удаляется всегда, в том числе после ошибки и Ctrl+C.
   Исходный файл удаляется после успеха, только если лежит внутри `INDEX_WORK_DIR`: файл из другого места
   считается оригиналом во внешнем хранилище и остаётся. Если удалить исходник не вышло (например, он открыт
   в плеере) или очистку прервали, фильм всё равно проиндексирован: в логе предупреждение, код выхода 0.

Метаданные берутся до эмбеддингов, хотя в #17393 п. 4 порядок обратный. Так строка в `movies` гарантированно
появляется раньше векторов, а неподходящий фильм отклоняется до долгих вычислений.

На CPU (4 потока torch) индексация идёт около 6 с на минуту фильма: фильм на 100 минут - около 10 минут.
Почти половина времени уходит на видео, треть - на звук. С видеокартой NVIDIA
и сборкой torch с CUDA (см. [Установка](#установка)) `ML_DEVICE=auto` выбирает её сам, в логе загрузки модели
появляется `device=cuda`. Векторы, посчитанные на GPU, совместимы с запросами, которые сервис считает на CPU.

## Переменные окружения

Читаются из `scripts/index/.env`, переменные окружения процесса важнее файла. `.env` в git не коммитится.
`.env` ML-сервиса из текущей папки скрипт не читает.

| Переменная | Обязательна | По умолчанию | Назначение |
|---|---|---|---|
| `TMDB_ACCESS_TOKEN` | одна из двух | | API Read Access Token TMDB, как у скрипта каталога |
| `TMDB_API_KEY` | одна из двух | | API Key (v3) TMDB |
| `DATABASE_URL` | да | | строка подключения к PostgreSQL, `postgresql://user:password@host:5432/db` |
| `ML_QDRANT_URL` | нет | `http://localhost:6333` | адрес Qdrant (REST) |
| `ML_QDRANT_API_KEY` | на dev-сервере | | API-ключ Qdrant; без него Qdrant с авторизацией отвечает `401 Unauthorized` |
| `ML_QDRANT_GRPC_PORT` | нет | `6334` | порт gRPC Qdrant |
| `ML_QDRANT_PREFER_GRPC` | нет | `true` | писать в Qdrant по gRPC |
| `ML_CACHE_DIR` | нет | `.cache/huggingface` | кэш весов моделей |
| `ML_LOCAL_FILES_ONLY` | нет | `false` | брать веса только из кэша, без обращения к huggingface.co |
| `ML_DEVICE` | нет | `auto` | `auto`, `cpu`, `cuda` или `mps` |
| `ML_TORCH_THREADS` | нет | `4` | потоки torch на CPU |
| `INDEX_WORK_DIR` | нет | `scripts/index/work` | рабочий каталог: временные папки и исходники, которые можно удалить после успеха |
| `INDEX_QDRANT_TIMEOUT_SECONDS` | нет | `60` | таймаут запросов к Qdrant; `ML_QDRANT_TIMEOUT_SECONDS` сервиса (2 с) рассчитан на поиск, а не на запись |
| `TMDB_REQUESTS_PER_SECOND` | нет | `20` | ограничение частоты запросов к TMDB, не больше 50 |

`ML_*_REVISION` тоже читаются, как в ML-сервисе, но менять их можно только вместе с сервисом и переиндексацией
всей коллекции.

## Подключение к production через SSH-туннель

Порты PostgreSQL и Qdrant production наружу не открыты. Адрес сервера и пользователь - в вики
«Схема_развертывания». Туннель пробрасывает три порта: PostgreSQL, Qdrant REST (6333) и Qdrant gRPC (6334):

```bash
ssh -N -L 5432:<адрес postgres>:5432 -L 6333:<адрес qdrant>:6333 -L 6334:<адрес qdrant>:6334 <пользователь>@<сервер>
```

Затем в `.env`: `DATABASE_URL=postgresql://...@127.0.0.1:5432/...`, `ML_QDRANT_URL=http://127.0.0.1:6333`
и `ML_QDRANT_API_KEY` - ключ Qdrant сервера.
Пишите именно `127.0.0.1`, а не `localhost`: под Windows `localhost` сначала пробует IPv6, и если порт
опубликован только на IPv4 (так делают Docker и `dejaview-infra`), каждое подключение ждёт таймаута.
Если 6334 пробросить нельзя, укажите `ML_QDRANT_PREFER_GRPC=false`: клиент будет писать по REST.
В `dejaview-infra` Qdrant публикует только REST-порт, поэтому для сервера из него нужен именно этот вариант.

## Локальная проверка

`compose.yaml` поднимает всё, что нужно утилите, без доступа к серверу: PostgreSQL 16 со схемой из
[`dejaview-docs`](https://github.com/dejaview-nsu/dejaview-docs/blob/main/contracts/db-schema.sql), Qdrant и
ML-сервис из этого репозитория. Нужен Docker. Команды - из корня репозитория.

```bash
curl -fsSLo scripts/index/db-schema.sql https://raw.githubusercontent.com/dejaview-nsu/dejaview-docs/main/contracts/db-schema.sql
docker compose -f scripts/index/compose.yaml up -d --build --wait
curl http://127.0.0.1:8000/health    # "status":"ok", все модели "ready", коллекции созданы
```

Первый запуск собирает образ ML-сервиса и ждёт загрузки моделей, это несколько минут. Веса берутся из
`.cache/huggingface` в корне репозитория, общего с утилитой. Схема применяется только при первом создании БД.

В `scripts/index/.env` для этого окружения:

```
TMDB_ACCESS_TOKEN=<ваш токен>
DATABASE_URL=postgresql://dejaview:dejaview_local_only@127.0.0.1:55432/dejaview
ML_QDRANT_URL=http://127.0.0.1:6333
```

Дальше обычный запуск: `python -m scripts.index movie.mp4 --movie-id 603`. Проверка, что фильм находится,
через API сервиса: первым в ответе `{"movie_ids":[...]}` должен быть `movie_id` фильма.

```bash
ffmpeg -v error -ss 00:30:00 -i movie.mp4 -frames:v 1 -update 1 -y scripts/index/work/frame.jpg
curl -X POST http://127.0.0.1:8000/v1/search/image -H "Content-Type: image/jpeg" --data-binary @scripts/index/work/frame.jpg
```

Клип (`/v1/search/video`, до 30 с), звук (`/v1/search/audio`, до 10 с) и описание сюжета
(`/v1/search/text`, `{"query": "..."}`) проверяются так же, см. README ML-сервиса. Кадры и клипы для проверки
удобно класть в `scripts/index/work/`: папка, как и файлы видео, картинок и звука в `scripts/index/`, в git
не попадает. Точки в Qdrant видны в панели http://127.0.0.1:6333/dashboard.

Под Windows в PowerShell вызывайте `curl.exe`, а не `curl`, и указывайте путь после `@` в кавычках, если в нём
есть пробелы или кириллица: `--data-binary "@C:\video\Снимок экрана.png"`.

Данные PostgreSQL и Qdrant лежат в томах и переживают перезапуск:

```bash
docker compose -f scripts/index/compose.yaml down       # остановить, проиндексированное сохранится
docker compose -f scripts/index/compose.yaml down -v    # остановить и удалить данные
```

## Коды выхода и что делать

Причина ошибки печатается одной строкой, трассировка - только с `-v`. При любой ошибке фильм остаётся
непроиндексированным (`indexed_at` не выставлен, поиском не находится), исходный файл не удаляется.
После исправления достаточно запустить ту же команду ещё раз.

| Код | Когда | Что делать |
|---|---|---|
| `0` | фильм проиндексирован | |
| `1` | сбой TMDB, PostgreSQL, Qdrant, ffmpeg или загрузки модели | см. сообщение: чаще всего не поднят туннель (`Не удалось подключиться к PostgreSQL`, `Сбой Qdrant`), нет коллекций (`нет коллекции`: запустите ML-сервис) или нет таблицы (`нет таблицы movies`: примените миграции backend) |
| `2` | ошибка настроек или аргументов: нет `.env`, ключа TMDB, `DATABASE_URL`, файла, ffmpeg; TMDB отклонил ключ | исправить `.env` или команду |
| `3` | файл не подходит (#17395 п. 2.3) или фильм отклонён TMDB (нет в TMDB, нет русского названия, описания или постера) | пережать файл командой из сообщения; для фильма - проверить `movie_id` |
| `130` | прервано (Ctrl+C) | временные файлы уже удалены, запустить заново |

## Тесты

```bash
pip install -r scripts/index/requirements-dev.txt
pytest scripts/index
```

Тесты нарезки и проверки файла генерируют маленькие видео ffmpeg-ом и пропускаются, если его нет.
Дополнительно, вне CI:

- `INDEX_TEST_DATABASE_URL=postgresql://...` - запись в `movies` на настоящем PostgreSQL, тест создаёт
  и удаляет схему `index_test`. Подойдёт PostgreSQL из [локальной проверки](#локальная-проверка):
  `postgresql://dejaview:dejaview_local_only@127.0.0.1:55432/dejaview`;
- `RUN_MODEL_TESTS=1` - индексация короткого ролика настоящими моделями и сравнение с векторами запросов
  (скачивает ~3 ГБ весов).
